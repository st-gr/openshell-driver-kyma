# Upstream v0.1.2 migration: schema-v2 config + delegated sandbox authentication — design

Status: approved (design), not yet implemented
Supersedes the `GATEWAY_REF=v0.0.116` pin in `.github/upstream-compat.env`.

## Problem

The chart is pinned to gateway `v0.0.116`. Upstream `v0.1.2` is a minor-version
bump that the pin's `PIN_REASON` records as "at least four separate breaking
changes". Two were already fixed version-compatibly (the `--drivers` selector,
and the config-must-be-a-regular-file mount). Two remain: the gateway
configuration schema, and the removal of `inference.local`.

The pin was taken to avoid discovering breakages one ten-minute CI run at a
time. This design covers the config schema and the change that actually hides
behind it — sandbox bootstrap authentication moved from the gateway into the
compute driver. `inference.local` is deliberately sequenced after (see
"Out of scope").

### Upstream did not drop external drivers

The migration was scoped on the assumption that upstream had overlooked
out-of-tree drivers reached over `--compute-driver-socket`. That assumption is
wrong, and the correction matters because it changes the work from "petition
upstream" to "follow upstream":

- `--compute-driver-socket` still exists at v0.1.2, and
  `[openshell.drivers.<name>].socket_path` is a first-class schema-v2 access
  path.
- Upstream tracks our exact configuration as a capability that must survive the
  migration. `e2e/configs/gateway/schema-v2-capability-parity.toml` carries
  `id = "external-compute-driver-socket"`, whose oracle reads: *"A selected
  non-reserved external driver connects through its configured Unix socket;
  legacy plural selector flags are rejected, while one `OPENSHELL_DRIVERS`
  environment value remains a deprecated upgrade alias when it does not
  conflict with canonical selection."*
- Upstream moved its **own** Kubernetes driver out of the gateway into a
  standalone binary (`crates/openshell-driver-kubernetes/src/main.rs`,
  configured by flags and env vars) — the same shape this driver already has.

`[openshell.drivers.<name>]` nesting predates v0.1.2. What v0.1.2 removed is the
gateway-scope *duplicates* that used to be merged in as defaults; upstream's
`driver_table_does_not_inject_gateway_values` test now pins that.

No upstream PR is required. The capability we would have asked for already
exists.

## Decisions

1. Migrate the chart's gateway TOML to schema v2. Empirically validated against
   the real `v0.1.2` binary, not inferred from source.
2. Implement `AuthenticateSandbox` in this driver and advertise
   `supports_sandbox_authentication = true`, rather than declining the
   capability and switching to a pre-minted sandbox token. This follows
   upstream's direction and preserves the projected-SA-token injection already
   proven on the cluster.
3. Move the create-only `tokenreviews` RBAC from the gateway ServiceAccount to
   the driver ServiceAccount.
4. Sequence the `inference.local` removal as separate work, so the auth
   delegation keeps an isolated bisect surface.

## Verification already performed

Ran the published `ghcr.io/nvidia/openshell/gateway:latest` image, which
reports `openshell-gateway 0.1.2`, against two candidate configs. Upstream
publishes commit-SHA image tags, not semver tags; `latest` is the v0.1.2 build.

What the chart renders today is rejected:

```
× failed to parse gateway config file: TOML parse error at line 6, column 1
  6 | sandbox_namespace = "openshell"
  unknown field `sandbox_namespace`, expected one of `name`, `bind_address`, ...
```

With `version = 1` and the rest migrated, it is still rejected:

```
× unsupported gateway config version 1; this build requires version 2;
  migrate legacy fields to the version 2 schema
```

The migrated config clears configuration parsing entirely and proceeds to
runtime startup (failing only on a container state-directory permission, which
is an artifact of running the image bare). That is the signal we wanted: the
parser accepts `version = 2`, the nested tables, and
`[openshell.drivers.kyma].socket_path`.

## Architecture

### Gateway configuration (schema v2)

`deploy/helm/openshell-driver-kyma/templates/gateway-config.yaml` renders:

```toml
[openshell]
version = 2

[openshell.gateway]
log_level = "<driver.logLevel>"

[openshell.gateway.auth]
allow_unauthenticated_users = <as today>

[openshell.gateway.gateway_jwt]
signing_key_path = "/etc/openshell-jwt/signing.pem"
public_key_path  = "/etc/openshell-jwt/public.pem"
kid_path         = "/etc/openshell-jwt/kid"
gateway_id       = "<gatewayId>"
ttl_secs         = <sandboxJwt.ttlSecs>

[openshell.drivers.kyma]
socket_path = "<driver.socket>"
```

Changes from today:

| Change | Why |
|---|---|
| `version = 1` → `2` | v1 is hard-rejected |
| delete gateway-scope `sandbox_namespace` | rejected; `rejects_removed_driver_fields_at_gateway_scope` names this exact key |
| drop `[openshell.drivers.kubernetes]` | `auth/k8s_sa.rs` is deleted upstream; nothing reads namespace/SA/`sa_token_ttl_secs` from gateway config any more |
| add `[openshell.drivers.kyma].socket_path` | the schema-v2 access path for an external socket driver |

The `auth` and `gateway_jwt` tables are already in their schema-v2 locations and
need no change — the chart nested them correctly when they were first written.

### Driver selection

The chart currently sets `OPENSHELL_DRIVERS=kyma` as an env var, chosen so one
chart worked across both gateway versions (`--drivers` at v0.0.116, which v0.1.2
rejects outright). With the floor moving to v0.1.x, switch to the canonical
`--compute-driver kyma` flag and drop the env var and its explanatory comment
block. `OPENSHELL_DRIVERS` survives at v0.1.2 only as a deprecated alias; there
is no reason to keep depending on it.

### Delegated sandbox authentication

v0.1.2 deletes the gateway's own Kubernetes ServiceAccount bootstrap
authenticator and replaces it with delegation to the compute driver. In
`crates/openshell-server/src/auth/compute_driver.rs`, on the single method
`/openshell.v1.OpenShell/IssueSandboxToken`, the gateway takes the `Bearer`
credential and calls:

```rust
let authenticated = self.compute.authenticate_sandbox(credential).await?;
```

This is backed by a new RPC in `proto/compute_driver.proto`, absent from
v0.0.116:

```protobuf
rpc AuthenticateSandbox(AuthenticateSandboxRequest)
    returns (AuthenticateSandboxResponse);

message AuthenticateSandboxRequest {
  string credential = 1 [(openshell.options.v1.secret) = true];
}
message AuthenticateSandboxResponse {
  string sandbox_id = 1;
  string runtime_identity = 2;
}
```

Declining the capability is not a no-op. `ComputeRuntime::authenticate_sandbox`
returns `Status::unimplemented("selected compute driver does not authenticate
sandbox credentials")` when `supports_sandbox_authentication` is false, so a
sandbox presenting its projected SA token would fail to bootstrap.

The sandbox side is unchanged: `OPENSHELL_K8S_SA_TOKEN_FILE` still exists at
v0.1.2 and `openshell-core`'s gRPC client still presents that token as
`Bearer`. This driver already injects it, and already projects the token with
audience `openshell-gateway` (`SA_TOKEN_AUDIENCE`, `provisioner.rs:97`) — the
same constant upstream's Kubernetes driver reviews against
(`SANDBOX_TOKEN_AUDIENCE`, `driver.rs:347`). No sandbox-side change is needed.

### `AuthenticateSandbox` algorithm

Ported from upstream's `crates/openshell-driver-kubernetes/src/driver.rs:845`,
which maps almost directly onto this driver's existing provisioning model:

1. `TokenReview` the credential with audience `openshell-gateway`.
2. From the review status, extract `(namespace, pod_name, pod_uid)` and require
   the ServiceAccount name to match the configured sandbox SA.
3. Reject namespaces this driver does not serve.
4. `GET` the pod; validate its UID against the UID in the token.
5. Derive `sandbox_id` from the pod's `openshell.ai/sandbox-id` label
   (`LABEL_SANDBOX_ID`, `helpers.rs:14`).
6. Resolve the owning `Sandbox` CR and validate the ownership link.
7. Return `sandbox_id` and `runtime_identity`.

Every failure is `unauthenticated` or `permission_denied`; only genuine
apiserver faults are `internal`. Credential values are never logged.

### `runtime_identity`

Upstream encodes `kubernetes://{namespace}/{resource_uid}/{pod_uid}`. This
driver uses `kyma://{namespace}/{sandbox_uid}/{pod_uid}`, where `sandbox_uid` is
the `Sandbox` CR's `metadata.uid`.

The gateway compares the identity returned by `AuthenticateSandbox` against the
one recorded when the sandbox was created, so the **same** value must also be
returned from `CreateSandbox` and `StartSandbox` (`runtime_identity` fields at
`compute_driver.proto:399` and `:432`). Populating only the authentication path
would leave the binding check comparing against an empty string. This is the
most likely defect in the whole migration and is called out as its own task.

### Capability reporting

`GetCapabilities` in `crates/openshell-driver-kyma/src/driver.rs:73` gains four
fields that did not exist at v0.0.116:

- `supports_sandbox_authentication: true`
- `driver_reports_runtime_readiness: false` — this driver does not report
  readiness itself, so the gateway additionally waits for the standard
  supervisor session, which is today's behaviour.
- `resource_capabilities` — the portable CPU/memory/GPU request forms this
  driver accepts.
- `resource_admission_policy` — see below.

`gateway_manages_lifecycle: false` and the empty extra-listener response are
unchanged and keep their existing rationale comments.

### Resource admission — not a free field

The proto describes an empty `resource_admission_policy` as denoting a legacy
driver "requiring explicit admission opt-out". That opt-out is **not** the
default. `ResourceAdmissionConfig::default()` in
`crates/openshell-core/src/resource_admission.rs:25` sets `enabled: true`, and
`verify_acknowledgement` accepts an empty value only when
`resource_admission.enabled` is false. Shipping an empty policy against a
default-configured gateway therefore fails the handshake.

Two consequences:

1. The driver emits an acknowledgement in upstream's format — the literal
   prefix `v1:` followed by the JSON serialisation of
   `{allow_driver_config, resource_admission}` — matching the gateway's
   effective policy. This driver does not depend on the `openshell-core` crate
   (it vendors the proto only), so the string is constructed locally and
   covered by a test asserting the exact format.
2. The default policy's `required_labels` are
   `openshell.ai/sandbox-attachable: "true"` and
   `openshell.ai/sandbox-attachable-workspace: <workspace placeholder>`.
   The placeholder is the literal `${workspace}`
   (`resource_admission.rs:13`), meaning the label's required value is the
   sandbox's own workspace name rather than a fixed string. Sandboxes this
   driver creates must carry both labels or admission rejects them, so the
   provisioner's label set is extended accordingly. Note the policy also
   reserves `LABEL_MANAGED_BY`, `LABEL_GATEWAY_ID`, and
   `LABEL_SANDBOX_WORKSPACE`, all of which this driver already sets.

The gateway records whatever the driver first reports and later re-checks that
it has not changed mid-session ("remote driver admission policy changed; restart
gateway after configuring matching policy"). It does not compare against a
gateway-side expected value, so the requirement is stability, not a specific
string.

## RBAC and chart wiring

`deploy/helm/openshell-driver-kyma/templates/clusterrole-tokenreview.yaml`
currently binds create-only `tokenreviews` to the **gateway** ServiceAccount.
The gateway no longer calls TokenReview; the driver does. The binding moves to
the driver ServiceAccount, and the file's explanatory comment is rewritten to
say why.

Steps 4 and 6 need `get` on pods and on `Sandbox` resources. The driver Role in
`role.yaml` already grants both (`pods: ["get"]`, `sandboxes: ["get", ...]`), so
the TokenReview binding is the only RBAC change.

## Migration — breaking

This is a coordinated chart-and-driver upgrade. A v0.1.2 gateway with an old
driver cannot bootstrap sandboxes (`unimplemented`), and a v0.0.116 gateway
rejects a schema-v2 config. The chart must ship both halves together, and the
gateway image pin lifts in the same change. There is no supported mixed state,
and the chart should not attempt to straddle both gateway versions as it did for
the selector flag.

Existing running sandboxes re-bootstrap on their next `IssueSandboxToken`
exchange, which is where the `runtime_identity` binding is checked. Sandboxes
created before the upgrade have no recorded identity to compare against, and
they will not carry the admission labels the default policy requires. The
rollout is therefore **drain-and-recreate**: delete existing sandboxes before
upgrading rather than attempting in-place continuity. This is acceptable because
the cluster is used only for testing this repo.

## Testing

- **Config**: `helm template` renders the schema-v2 TOML; assert
  `version = 2`, absence of `sandbox_namespace`, presence of
  `[openshell.drivers.kyma].socket_path`. Feed the rendered file to the real
  v0.1.2 gateway image and assert it clears config parsing — the same harness
  used to validate this design, promoted into CI.
- **Unit**: `AuthenticateSandbox` against a mocked TokenReview — accepted token;
  wrong audience; wrong ServiceAccount; unserved namespace; pod UID mismatch;
  missing pod; missing/again-mismatched owner. Assert the status codes, and
  assert the credential never appears in log output.
- **Identity**: assert `CreateSandbox`, `StartSandbox`, and `AuthenticateSandbox`
  return byte-identical `runtime_identity` for the same sandbox.
- **Admission**: assert the acknowledgement string matches the exact `v1:{json}`
  format, and that a provisioned sandbox carries every label in the default
  `required_labels` set.
- **Smokes**: `interop-smoke.sh` and `managed-smoke.sh` unpinned, against
  v0.1.2. These already exercise create/stop/start and a real bootstrap, so a
  broken delegation path fails them.
- **Cluster**: deploy and verify create/stop/start end-to-end before the pin
  removal is considered settled.

## Implementation phasing

1. Land the proto re-vendor to v0.1.2 (PR #70 carries it). Nothing else can
   compile against `AuthenticateSandbox` until this is in.
2. `runtime_identity` derivation, returned from `CreateSandbox` and
   `StartSandbox`.
3. `AuthenticateSandbox` plus the capability flags.
4. Resource admission: the `v1:` acknowledgement string and the sandbox
   admission labels. Independent of 3 and separately testable.
5. RBAC move and chart config migration.
6. Unpin `GATEWAY_REF`, correct `PIN_REASON`, clear `PIN_BLOCKED_BY`, run both
   smokes, deploy.

Steps 2, 3, and 4 are separable and independently testable. Step 5 is mechanical
but must not land before 3 and 4, or the deployed gateway delegates to a driver
that cannot answer and rejects its sandboxes at admission.

## Out of scope

- **`inference.local` removal** and the move to `provider_profile_sources`.
  Sequenced as separate work by decision. `scripts/check-inference-local.sh`
  already detects it, and the `PIN_BLOCKED_BY` note keeps naming it until it is
  done.
- Upstream contribution. The external-driver capability already exists.
- Adopting upstream's standalone `openshell-driver-kubernetes` binary. Kyma
  provisioning differs enough that the existing driver stays.
- `credential_drivers`, `provider_profile_sources`, and the other schema-v2
  surfaces this chart does not use.

## Correction to the pin's recorded reason

`.github/upstream-compat.env` says "of the six fields this chart emits, only
`log_level` is still valid at top level". That reads as a wholesale schema
rewrite. The accurate statement is narrower: four of the six were already in
their correct nested locations; only `version` (value) and `sandbox_namespace`
(placement) are invalid. The `PIN_REASON` text is corrected as part of step 5
so the record does not overstate the drift.
